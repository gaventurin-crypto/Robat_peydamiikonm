ربات تلگرام مدیریت درخواست‌ها
نسخهٔ اولیهٔ اجرایی با Python 3.12، aiogram 3.31 و SQLite. پنل کاربر و مدیر داخل گفت‌وگوی خصوصی ربات است. متن خوشامدگویی و اطلاعیه تا زمان بازبینی مالک، «پیش‌نویس» هستند؛ قبل از استفادهٔ عمومی باید متن، مبنای قانونی پردازش و مجوز ارائهٔ خدمت بررسی شوند.
این نرم‌افزار فقط درخواست‌ها و مکاتبات را مدیریت می‌کند. هیچ جست‌وجو یا اتصال به پایگاه دادهٔ دولتی، بانکی یا خصوصی ندارد. پرداخت یا تصمیم مدیر به‌تنهایی مجوز دسترسی یا افشای اطلاعات اشخاص نیست.
فایل‌ها
app/domain.py: گزینه‌های ثابت، برچسب‌ها و قواعد انتقال وضعیت.
app/database.py: SQLite، پرونده، پیش‌نویس، پیام، رسید، audit، استثنای قانونی و پاک‌سازی.
app/user_handlers.py: ثبت درخواست، انتخاب پرونده و مکاتبهٔ کاربر.
app/admin_handlers.py: پنل خصوصی مدیر، فهرست، جست‌وجو، تصمیم دستی و پاسخ.
app/media.py: سقف اندازه، امضای فایل و اعتبارسنجی اسناد.
app/main.py: راه‌اندازی polling و حذف زمان‌بندی‌شده.
tests/: آزمون‌های خودکار دامنه، دسترسی، پایگاه‌داده، پیکربندی و فایل.
requirements.txt و requirements-dev.txt: وابستگی‌های دقیق نسخه‌دار.
.env.example: نمونهٔ تنظیمات، بدون توکن واقعی.
Dockerfile: تصویر اجرا با کاربر غیرممتاز و مسیر دادهٔ جدا.
اجرای محلی
پیش‌نیاز: Python 3.12 یا جدیدترِ پشتیبانی‌شده توسط سرویس، Git، و رباتی که با BotFather ساخته شده باشد.
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
فایل .env را فقط در محیط امن میزبان ویرایش کن؛ هرگز آن را در Git یا پیام عمومی بارگذاری نکن. مقدار TELEGRAM_BOT_TOKEN را از BotFather و ADMIN_TELEGRAM_ID را به شناسهٔ عددی حساب مدیر تغییر بده. شناسهٔ عددی را از یک ربات معتبر دریافت کن و با گفت‌وگوی خصوصی ربات آزمایش کن. مدیر دقیقاً یک نفر است.
python -m app.main
توقف محلی: Ctrl+C. در میزبان کانتینری، گزینهٔ Stop را بزن. توقف ربات اطلاعات پایدار را پاک نمی‌کند؛ برای حذف امن باید ابتدا سرویس را متوقف کنی و سپس volume داده را طبق سیاست قانونی حذف کنی.
آزمون
python -m pytest -q
آزمون‌ها بدون توکن واقعی اجرا می‌شوند. برای آزمون زنده، با دادهٔ ساختگی یک درخواست با چند نوع اطلاعات و مقدار مستقل ثبت کن؛ سپس شروع گفتگو توسط مدیر، تبادل چند پیام و Reply، پایان گفتگو، رسید، restart و پاک‌سازی را بررسی کن. هیچ دادهٔ واقعی یا حساس را برای آزمایش نفرست.
تنظیمات
TELEGRAM_BOT_TOKEN: اجباری و محرمانه.
ADMIN_TELEGRAM_ID: اجباری، شناسهٔ عددی مثبت؛ کنترل سمت سرور و محدود به گفت‌وگوی خصوصی.
DATABASE_PATH: پیش‌فرض data/bot.sqlite3؛ روی میزبان، مسیر volume پایدار باشد.
CASE_RETENTION_HOURS: پیش‌فرض ۲۴ ساعت پس از رد/تکمیل/لغو؛ فقط با توجه به الزام قانونی تغییر بده.
MAX_UPLOAD_MB: پیش‌فرض ۱۰، بازهٔ برنامه ۱ تا ۲۰ مگابایت. محدودیت API و میزبان ممکن است کمتر باشد.
WELCOME_TEXT, PRIVACY_NOTICE, NOTICE_VERSION, HAVE_QUESTION, NEED_QUESTION, DESCRIPTION_QUESTION, FILE_HELP_TEXT: متن قابل تغییر؛ متن‌های فعلی پیش‌نویس‌اند.
INFO_OPTIONS_ORDER: جایگشت دقیق شش گزینهٔ پایه با جداکنندهٔ |. فرم علاوه بر این گزینه‌ها «شناسه کاربری» و «سایر موارد» را می‌پذیرد؛ برای هر گزینهٔ انتخاب‌شده مقدار جداگانه ثبت می‌شود.
استقرار
مخزن GitHub در ۱۴ اکتبر ۲۰۲۶ به‌صورت Private بررسی شد. سرویس میزبانی هنوز انتخاب یا ساخته نشده و ربات زنده اجرا نشده است؛ استقرار تأییدنشده است. از تلفن Android و مرورگر:
۱. در GitHub وارد حساب شو و از New repository یک مخزن Private بساز. دسترسی عمومی نده و Secrets را در issue، commit یا گفت‌وگوی عمومی ننویس.
۲. فایل‌های همین پروژه را در مخزن خصوصی قرار بده. .env و پوشهٔ data/ نباید بارگذاری شوند؛ .gitignore آن‌ها را مستثنا می‌کند. پس از اتمام این مرحله، نتیجه را بررسی کن.
۳. یک میزبان دارای اجرای Docker یا Python، worker دائمی و دیسک پایدار انتخاب کن. پیش از ساخت سرویس، صفحهٔ قیمت و مستندات جاری میزبان را برای خواب خودکار، محدودیت ساعت/مصرف، restart، منطقهٔ دسترسی و ماندگاری volume بخوان. پلن رایگان را ۲۴/۷ یا پایدار فرض نکن؛ بسیاری از پلن‌ها worker را می‌خوابانند، volume پایدار نمی‌دهند یا می‌توانند سهمیه را تغییر دهند. اگر volume پایدار، دسترسی محدود و سیاست پشتیبان‌گیری روشن ندارد، برای دادهٔ پرونده‌ای مناسب نیست. هیچ پلن پولی را بدون تأیید مالک فعال نکن.
۴. سرویس را از مخزن خصوصی بساز و Dockerfile را انتخاب کن. TELEGRAM_BOT_TOKEN و ADMIN_TELEGRAM_ID را در بخش Environment/Secrets میزبان وارد کن، نه در سورس. سایر متغیرها را از .env.example تنظیم کن. اگر میزبان تنظیم Secret ندارد، استقرار را متوقف کن.
۵. یک volume پایدار و خصوصی را به /data وصل کن؛ در تنظیمات سرویس DATABASE_PATH=/data/bot.sqlite3 قرار بده. اگر میزبان volume پایدار ندارد، از دادهٔ واقعی استفاده نکن. SQLite برای یک worker و یک نسخهٔ ربات است؛ چند replica یا چند پردازش هم‌زمان را فعال نکن.
۶. Deploy کن و لاگ را برای bot polling started بررسی کن. لاگ نباید token، متن پرونده، شناسهٔ فایل یا اطلاعات حساس نشان دهد. اگر ربات اجرا نشد، token را داخل چت نفرست؛ آن را مستقیماً در بخش Secret میزبان جایگزین کن.
۷. با حساب مدیر به ربات پیام بده و /start را بزن. فقط شناسهٔ عددی ثبت‌شده باید پنل را ببیند. با حساب آزمایشی دیگر، نبود پنل مدیریت را بررسی کن.
۸. یک درخواست ساختگی با چند نوع اطلاعات و مقدارهای مستقل ثبت کن؛ شمارهٔ R-... و اعلان شامل مشخصات کاربر و مقادیر را بررسی کن. از اطلاعات شخص واقعی استفاده نکن.
۹. برای پروندهٔ آزمایشی پیام متنی، عکس، ویس و PDF مجاز بفرست و ارسال پاسخ مدیر به پروندهٔ انتخاب‌شده را آزمایش کن. یک فایل اجرایی آزمایشی را ارسال نکن؛ در صورت دریافت، باید رد شود. رسید را فقط در حالت انتظار پرداخت بفرست و بررسی کن خودش پرداخت را تأیید نمی‌کند.
۱۰. بعد از بسته‌شدن پروندهٔ آزمایشی، برای آزمایش حذف می‌توانی در سرویس آزمایشی CASE_RETENTION_HOURS=1 تنظیم کنی. پس از بیش از یک ساعت، وضعیت EXPIRED و نبود متن/پیام/فایل در پایگاه را بررسی کن؛ سپس مقدار مصوب را برگردان. این آزمون روی دادهٔ واقعی انجام نشود.
۱۱. سرویس را restart کن و بررسی کن پروندهٔ باز باقی مانده باشد. مطمئن شو volume به همان مسیر متصل مانده است. نتیجهٔ هر مرحله را ثبت کن و بعد به مرحلهٔ بعد برو.
معماری و پایگاه داده
Handlerها در این نسخه مستقیماً Database را صدا می‌زنند. برای یک ربات کوچک و یک SQLite worker، لایهٔ Service که فقط متدها را forward کند ارزش کافی ندارد؛ قواعد دامنه در domain.py و orchestration تلگرام در handlerهاست. افزودن Repository/Service در صورت رشد منطق یا نیاز به backend دوم قابل بررسی است. SQLAlchemy و Alembic اضافه نشده‌اند؛ schema upgradeهای فعلی SQLite در Database.initialize انجام می‌شوند و آزمون upgrade بدون از دست‌رفتن داده دارند. PostgreSQL backend پشتیبانی‌شده نیست و فقط با migration واقعی و integration test برای هر دو dialect باید معرفی شود.
SQLite با WAL برای یک process/worker و یک volume پایدار است؛ چند replica یا چند پردازش را روی همان فایل فعال نکن. برای snapshot سازگار، از SQLite online backup API در app/backup.py استفاده کن؛ فایل اصلی را هنگام کار ربات مستقیماً کپی نکن:
python -c 'from app.backup import create_backup; create_backup("data/bot.sqlite3", "/secure/private-backups/request-bot-backup-20261014.sqlite3")'
مقصد باید در volume خصوصی و رمزگذاری‌شده، خارج از مخزن و log باشد. تابع با مجوز فایل 0600 می‌سازد و فایل موجود را جایگزین نمی‌کند. برای بازیابی، ابتدا ربات را متوقف کن و به فایل تازه‌ای restore کن؛ مقصد موجود عمداً رد می‌شود:
python -c 'from app.backup import restore_backup; restore_backup("/secure/private-backups/request-bot-backup-20261014.sqlite3", "data/recovered.sqlite3")'
Backup و پاک‌سازی آن دستی‌اند؛ سرویس زمان‌بندی‌شده یا حذف خودکار backup در این نسخه وجود ندارد. CASE_RETENTION_HOURS و پاک‌سازی پرونده فقط روی پایگاه زنده اثر می‌گذارند، نه snapshot، backup میزبان یا نسخهٔ کپی‌شده. هر backup حاوی دادهٔ شخصی باید در سیاست نگهداری، تاریخ انقضا و حذف جداگانه داشته باشد؛ تا حذف آخرین backup حاوی پرونده، حذف داده از سامانه کامل نیست. TTL backup باید پیش از استفادهٔ واقعی تعیین و اجرای حذف آن جداگانه پایش شود. فایل‌های upload موقت با خروج از TemporaryDirectory حذف می‌شوند؛ این تضمین شامل دیسک میزبان، snapshot، دستگاه کاربر یا سرور Telegram نیست. Restore باید روی محیط آزمایشی و با دادهٔ ساختگی اعتبارسنجی شود.
Docker محلی
docker build -t request-management-bot:local .
docker volume create request-bot-data
docker run -d --name request-management-bot --restart unless-stopped \
	--env-file .env -e DATABASE_PATH=/data/bot.sqlite3 \
	--mount source=request-bot-data,target=/data \
	request-management-bot:local
docker logs --tail 100 request-management-bot
docker stop request-management-bot
این فرمان فقط برای Docker محلی روی دستگاه خصوصی است؛ متغیرهای محیطی در metadata کانتینر قابل مشاهده‌اند. در میزبان اشتراکی Secretهای پنل میزبان را به‌کار ببر. فایل .dockerignore فایل‌های secret، پایگاه‌داده و artifactهای محلی را از build context خارج می‌کند.

امنیت و عیب‌یابی
مخزن فعلی Private است، اما تغییرات محلی هنوز commit نشده‌اند. فایل .env در Git ثبت نیست؛ اگر token هرگز در تاریخچهٔ مخزن عمومی قرار گرفته، از BotFather باطل و جایگزینش کن.
CI workflow هم‌اکنون در working tree وجود ندارد؛ اجرای تست/audit/build خودکار GitHub تأیید نشده است.
rate limit در SQLite روی پیام و callback خصوصی اعمال می‌شود و برای یک process است؛ گفتگوی فعال بودجهٔ بالاتری دارد. چند replica به limiter مشترک و backend مناسب نیاز دارد.
فایل‌ها به سقف حجم و signature واقعی بررسی می‌شوند؛ دانلود موقت است و محتوا اجرا نمی‌شود. mediaهای Telegram در سرور محلی ذخیره نمی‌شوند.
خطای TELEGRAM_BOT_TOKEN: مقدار Secret را در میزبان بررسی/تعویض کن؛ هرگز آن را در چت یا log نفرست. خطای conflict polling: فقط یک process برای هر token اجرا کن.
پرونده بعد از restart ناپدید شده: مسیر volume و DATABASE_PATH=/data/bot.sqlite3 را بررسی کن. فایل رد شده: MIME/signature، نام یا اندازه با allowlist سازگار نیست.
audit مستقل امنیتی، آزمون زندهٔ Bot API، بازیابی backup و استقرار میزبان هنوز انجام نشده‌اند. هیچ ادعای ناشناس‌بودن مطلق، امنیت کامل، حذف از دستگاه کاربر یا availability دائمی وجود ندارد.
در این نسخه رسانه‌ها محلی دانلود و نگهداری نمی‌شوند؛ شناسهٔ رسانه و ارجاع پیام برای مکاتبه در SQLite ذخیره می‌شود. Bot API امکان حذف پیام تحویل‌شده از دستگاه کاربر، حذف نسخه‌های ذخیره‌شده یا کنترل backup میزبان را تضمین نمی‌کند. حذف SQLite نیز معادل حذف از تمام نسخه‌ها نیست. backup خودکار volume را خاموش کن، مگر آنکه ضرورت قانونی و رمزگذاری/مهلت حذف آن تصویب شده باشد. فشرده‌سازی/WAL و snapshot میزبان هم ممکن است نسخهٔ قدیمی باقی بگذارند؛ این نسخه تضمین پاک‌سازی امن سکتور دیسک یا نسخه‌های میزبان را نمی‌دهد.
قواعد و محدودیت‌های مهم
ارسال دریافت‌کننده فقط با Bot API و هویت ربات انجام می‌شود؛ مالکیت ربات ممکن است از راه‌های دیگر قابل استنباط باشد و ناشناسی مطلق وعده داده نمی‌شود.
رسید در وضعیت RECEIPT_REVIEW می‌ماند تا مدیر دکمهٔ تأیید را بزند. مدیر می‌تواند رسید را رد کند یا درخواست دست‌نویسِ رسید/توضیح مجدد بفرستد؛ پس از ارسال موفق، پرونده به AWAITING_PAYMENT برمی‌گردد. رسید یا پرداخت، دسترسی به دادهٔ اشخاص ایجاد نمی‌کند.
پاسخ‌های رد/تأیید/درخواست اطلاعات/پرداخت را مدیر شخصاً می‌نویسد. ثبت تأیید درخواست، فقط وضعیت را عوض می‌کند و متن خودکار برای کاربر نمی‌سازد.
فایل‌های قابل قبول: عکس تلگرام، voice، PDF، PNG، JPEG، WebP، متن ساده، OGG و MP3؛ اسناد با امضای محتوا بررسی و در temporary directory حذف می‌شوند. سقف و محدودیت Bot API/میزبان اعمال می‌شود. فایل‌های ویدئو، آرشیو و اجرایی پشتیبانی نمی‌شوند.
اطلاعاتی مانند نام، آدرس، تلفن، کد ملی، تاریخ تولد و شمارهٔ کارت حساس‌اند. فقط در صورت ضرورت و مجاز بودن جمع‌آوری کن؛ رمز، OTP، PIN، CVV2 یا اطلاعات ورود بانکی هرگز درخواست یا ذخیره نمی‌شود.
پاک‌سازی هر ساعت پرونده‌هایی را که حداقل مدت تنظیم‌شده از بسته‌شدنشان گذشته و «توقف حذف خودکار» ندارند، به EXPIRED می‌برد و متن، پیام، رسید، اتصال کاربر و session بلااستفاده را از SQLite حذف می‌کند. مدیر برای پروندهٔ مشمول الزام قانونی، از جزئیات پرونده «توقف حذف خودکار» را می‌زند؛ برداشتن توقف نیز تأیید دومرحله‌ای دارد. audit حداقلیِ رویداد حذف/توقف باقی می‌ماند. مهلت ۲۴ ساعت مقدار اولیه است، نه نظر حقوقی؛ فقط با مبنای مصوب استفاده کن.
اتصال SQLite از secure_delete استفاده می‌کند و پس از پاک‌سازی WAL را checkpoint/truncate می‌کند. این کار جلوی بازیابی ساده از صفحه‌های آزادشده را می‌گیرد، اما پاک‌سازی امن سکتور، snapshot، backup یا نسخه‌های میزبان را تضمین نمی‌کند.
SQLite، دیسک میزبان، لاگ میزبان و backup خارج از اختیار کامل برنامه‌اند. دسترسی به فایل DB و volume را محدود کن. نسخهٔ آزمایشی را پیش از استفادهٔ عمومی از نظر امنیت و قانون بررسی کن.
